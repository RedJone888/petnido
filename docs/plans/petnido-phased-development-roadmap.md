# Petnido 分阶段开发任务路线图

> 文档状态：总体开发路线图
> 编制日期：2026-08-04
> 适用范围：以现有 Petnido 代码、数据库和页面为基础，实现已确认项目计划
> 不包含：支付、评价、运营与治理

## 1. 路线图目标

Petnido 不是从零开发，也不能把现有代码直接视为成品。当前项目已经具备 Next.js、NextAuth、tRPC、Prisma、Dashboard 框架、部分公开页面、旧版需求/服务发布表单、附件处理和新版需求步骤表单等基础；同时存在字段不足、页面与数据库不匹配、越权风险、Mock 数据、假成功状态、缺失流程和移动端问题。

本路线图采用以下方法：

1. 保留已经验证且符合目标的技术基础和界面资产。
2. 改造已经连通数据库但业务语义不足的功能。
3. 融合旧版真实持久化能力与新版步骤式交互，而不是二选一。
4. 为缺失的业务闭环补充领域模型、API 和页面。
5. 在新功能完成对账和回退验证后，再逐步退出旧逻辑。

任务以“可独立交付的功能模块”为颗粒度，不拆成单个字段、按钮或文件级任务。每个阶段结束后进行阶段验收，验收未通过不进入依赖阶段。

## 2. 现有内容的处理策略

### 2.1 直接保留并继续使用

- Next.js、TypeScript、NextAuth、tRPC、Prisma 的总体技术架构。
- 现有首页的主要视觉方向和基础组件体系。
- Dashboard 的布局、导航框架、加载与错误边界。
- 第一批建立的状态机、Zod 合同、位置隐私合同、CI 和测试框架。
- 已验证的附件上传、照片分类和事务关联思路。
- 现有三语言资源组织方式，但需要补齐和统一文案。

### 2.2 改造后复用

- 旧需求发布：复用数据库调用、事务、附件关联、创建/编辑入口；改造字段模型、权限、地址、金额、宠物快照和状态命令。
- 旧服务发布：复用 ServiceProfile 关联、照片、价格规则、时间和编辑管理；补齐三种模式字段、所有权、档案默认值、可用性和归档。
- 新版需求步骤表单：复用模式化引导、预览、草稿和丰富字段；拆分超大组件、修复移动端、统一合同并接入真实事务。
- 公开需求页：复用卡片和基础布局；改为游客 API、真实筛选、稳定分页和公开 DTO。
- 个人中心：复用页面外壳；将消息、通知、匹配、设置等本地 Mock 替换为真实服务端数据。
- 地图搜索：复用选点能力；持久化前转换为只含经纬度和非精确区域标签的 `MapLocation`。

### 2.3 融合重建

- Need、Service、Pet、Location、Application、Booking、Conversation、Favorite 和 Notification 的领域模型。
- 新旧发布表单到统一 Draft/Command 的 mapper。
- 公开 DTO 与 Owner DTO 的严格边界。
- 应聘、预约、确认、取消和重新公开的完整状态闭环。
- 服务可用时间、寄养容量和预约时间冲突模型。

### 2.4 验证后淘汰

- 页面内硬编码的需求、服务者、消息、通知和匹配数据。
- 只修改 React state/localStorage 就显示成功的收藏、应聘、预约和设置操作。
- `addressRaw`、`areaRaw`、`baseAreaRaw` 等精确地址持久化路径。
- 允许前端提交任意状态的 mutation。
- 新流程稳定后重复的旧新建入口和旧数据 mapper；删除前必须完成对账、回退和稳定期。

- 页面、路由、API、Mock、重复领域逻辑和数据库现状审计。
- 新旧需求发布流程比较和主要冲突登记。
- Need、Service、Application、Booking、Conversation 状态机。
- 权限矩阵、位置隐私合同、Money 和发布接口合同。

- 上门需求、过期和寄养容量的隔离验证切片。

### 阶段结论

允许继续开发，但当前不允许生产数据迁移或公开市场上线。第一批发现的问题必须作为后续任务输入，不能把验证切片当成已经完成的正式功能。

## 5. 阶段 1：安全与服务端事实来源

### 任务 1.1：需求、服务和服务档案权限加固

集中修复 Need、Service、ServiceProfile 的读取、修改、状态变化和归档权限。数据库写条件必须包含 owner/participant，公开 DTO 和所有者 DTO 分离，非本人访问统一返回不可枚举的错误。现有合法页面应保持可用。

**完成标准**：owner、非 owner、游客和伪造 ID 回归测试通过；不存在按资源 ID 无条件修改；前端不再提交任意状态。

### 任务 1.2：认证和验证码安全闭环

完善验证码发送限流、过期、最大尝试次数、一次性消费、并发重放保护、session 失效处理和日志脱敏。建立稳定错误码与三语言错误键。

**完成标准**：正常、超限、错误、过期、重复消费和并发验证全部通过；日志不包含验证码、完整邮箱、邮件正文或 token。

### 任务 1.3：统一命令、错误和幂等基础

将通用 `updateStatus` 替换为领域命令；为发布、收藏、应聘、预约、确认等未来写操作建立统一错误 envelope、idempotency key 和冲突响应方式。页面成功状态必须来自服务端结果。

**完成标准**：状态机和 API 使用相同命令语义；重复请求不会重复创建记录；现有 Mock 成功入口被禁用或明确标记。

### 阶段 1 验收

- 所有已知越权 P0 清零。
- 认证安全测试和错误恢复 E2E 通过。
- 旧需求、旧服务合法管理功能无回归。
- `npm run quality` 和 production build 通过。

## 6. 阶段 2：账号、档案与首次引导

详细执行清单见 [第二批开发任务](./batch-2-foundation-and-onboarding.md)。

### 任务 2.1：Profile、Pet、UserLocation 数据与 API

通过 expand migration 增加个人资料、宠物档案和地图位置结构，并实现本人 CRUD、归档和默认值接口。位置只保存经纬度及可选非精确区域标签；宠物健康和照护信息属于受保护资料。

**完成标准**：空库迁移、脱敏旧数据 dry-run、所有权、默认位置唯一性和 Public DTO 隐私测试通过；不执行生产 migration。

### 任务 2.2：首次注册与非首次登录流程

实现服务端 onboarding 状态、头像昵称页和意图选择。首次用户走“资料 → 意图”，选择提供服务时确认开启接单模式；非首次用户直接进入个人中心，不弹出查看消息提示。

**完成标准**：首次、中断恢复、非首次、重复确认和取消开启接单模式 E2E 通过。

### 任务 2.3：个人、宠物、位置和服务档案页面

在个人中心实现资料编辑、宠物档案、地图位置和服务档案基础管理。服务档案包含经验介绍、默认服务位置、常用货币和接单总开关；同一用户可以同时发布需求和提供服务。

**完成标准**：桌面、390px、键盘和 200% 缩放验收通过；数据由服务端持久化，无本地假保存。

### 任务 2.4：登录回跳与待执行动作框架

为收藏、咨询、应聘和预约建立签名 PendingAction。登录后回到原详情并由用户确认一次；首次注册必须先完成 onboarding；过期、篡改、目标失效和重复执行均可处理。

**完成标准**：无开放重定向，不信任 localStorage 动作，不重复创建业务记录；尚未实现的动作明确显示未开放。

### 任务 2.5：Dashboard 认证入口与通知偏好基础

修复未登录个人中心死胡同，补齐认证失败、会话过期、无权限和资源不存在页面；建立邮件通知偏好数据和设置入口，但暂不发送业务邮件。

**完成标准**：Dashboard 登录回跳、异常恢复、通知偏好持久化和三语言冒烟通过。

### 阶段 2 验收

- 已确认的首次/非首次用户轨迹完整可运行。
- 档案具备稳定服务端事实来源和权限隔离。
- 发布流程以后可以在相应步骤读取宠物、位置、服务位置和货币默认值。
- 发布表单尚未正式接库，不出现假发布成功。

## 7. 阶段 3：需求与服务发布体系

### 任务 3.1：新旧发布能力融合与目标数据结构

对新版需求步骤表单、旧需求表单、现有服务表单、tRPC 和 Prisma 逐字段比较。六种模式分别形成 `KEEP/TRANSFORM/REPLACE/DEFER` 矩阵；建立版本化 Draft、正式 Publish Command、模式明细、宠物/位置/价格快照、任务和可用性数据结构。

这项任务不选择整套旧页面或整套新页面，而按能力取舍：新版贡献引导和业务问题，旧版贡献持久化、附件、编辑与后台经验，最终共同适配新的领域合同。

**完成标准**：项目计划中的所有发布字段都有目标字段、校验、公开性、快照和迁移归属；V2 migration 只 expand，旧数据 dry-run 可对账。

### 任务 3.2：统一发布流程框架

拆分新版超大组件，建设需求/服务共用的步骤导航、草稿版本、宠物选择、位置、日期时间、Money、附件和预览能力；创建与编辑复用同一组模式组件。修复桌面横向裁切和移动端破版。

**完成标准**：1440px、1024px、390px、键盘和 200% 缩放通过；刷新可恢复草稿；损坏或旧版本草稿可迁移/清除。

### 任务 3.3：三模式需求发布与管理

依次完成上门、寄养、自定义需求：

- 上门：宠物、日期、上门频率、每天次数、期望时间、逐宠物逐次任务、位置、预算和交通费。
- 寄养：宠物、时间、双方物资、每日和定期任务、环境要求、不可接受条件、接送、距离、预算及额外费用。
- 自定义：宠物、时间、位置、任务和金额。

发布事务成功后才写回新宠物和位置档案；业务记录保存发布时快照。支持预览、编辑、关闭、取消、已匹配后移除服务者并在未过期时重新公开。

**完成标准**：三模式创建/编辑往返无字段丢失；失败原子回滚；重复提交幂等；`endsAt` 到达即公开过期；没有新写入旧 Raw 地址。

### 任务 3.4：三模式服务发布与管理

完成上门、寄养、自定义服务：

- 上门：服务位置和范围、复杂可用时间、宠物政策、经验证明、任务、价格与优惠。
- 寄养：宠物政策、时间、寄养地图位置、环境照片和其他宠物、物资条件、价格优惠及最大宠物容量。
- 自定义：时间、位置、内容、宠物类型、价格、经验和照片。

发布时从服务档案读取位置和货币默认值，允许单次修改；成功后按合同更新服务档案默认值。支持编辑、暂停、恢复和归档。

**完成标准**：三模式事务、编辑回显、所有权和 Public DTO 测试通过；BOARDING 以宠物数量作为容量，其他模式不使用容量字段。

### 任务 3.5：新旧双轨、数据兼容和入口切换准备

用 feature flag 运行新旧路径，在测试环境对同类输入的记录、关联、公开 DTO 和编辑回显进行对账。旧记录通过明确 mapper 读取，无法可靠映射的字段提示用户确认，不能静默丢失或复制精确地址。

**完成标准**：关闭新入口 flag 后新数据仍可读取；未删除旧代码和旧字段；对账无未解释差异；完成回滚演练后才允许灰度切换。

### 阶段 3 验收

- 六种发布模式都真实写入测试数据库且可编辑回显。
- 旧发布功能仍可回退，新版不再是假发布。
- 档案读取和成功后写回规则符合确认后的用户轨迹。
- 发布成功页已准备匹配与通知响应合同，但不伪造尚未实现的结果。

## 8. 阶段 4：公开市场与发现

### 任务 4.1：需求公开列表、详情与筛选

实现游客可用的需求列表和详情。筛选覆盖地点半径、预算、宠物类型、任务类别、时间和模式；使用稳定 cursor 分页。只有 OPEN 且未过期需求公开，收藏和所有者页面仍可读取过期记录。

**完成标准**：过期边界、筛选组合、分页稳定性、Public DTO 和地图隐私测试通过。

### 任务 4.2：服务与服务者公开市场

实现服务列表、服务详情和服务者公开档案，展示公开经验、服务位置范围、服务模式、宠物政策、价格、照片和当前日期的成功预约数量。未登录用户可浏览，预约前才要求登录。

**完成标准**：真实数据库数据替换服务者 Mock；暂停/归档服务不进入公开搜索；公开资料不泄露私有默认位置和内部附件。

### 任务 4.3：收藏和公开页面交互基础

实现需求/服务收藏的服务端幂等操作和收藏列表。收藏中的过期需求保留并标记；详情页提供咨询、应聘、预约入口并连接 PendingAction。

**完成标准**：刷新、跨设备和重复点击状态一致；收藏过期规则正确；游客登录回跳可恢复。

### 任务 4.4：模式说明和照护知识入口

完成需求/服务三种模式的介绍页面；建立照护知识分类列表，按宠物类型和照顾事项分类，内容可为标题、摘要和外部来源链接，并记录来源和免责声明。

**完成标准**：三语言路由和元数据完整；链接可用且来源明确；不把外部内容复制为无来源的站内文章。

### 阶段 4 验收

- 游客可以完成“附近需求 → 详情”和“附近服务/服务者 → 详情”两条路径。
- 所有展示数据来自服务端，不再使用业务 Mock。
- 搜索、收藏、过期和位置隐私规则一致。

## 9. 阶段 5：会话、应聘与预约

### 任务 5.1：Conversation、Message 与站内聊天

建立会话、参与者、消息、已读状态和系统消息模型。需求咨询、服务咨询、应聘和预约复用同一业务上下文会话；双方可在平台实时或轮询聊天，消息归档但不物理删除。

**完成标准**：只有参与者可读写；消息分页、幂等发送、已读和会话复用测试通过；Dashboard 消息 Mock 全部移除。

### 任务 5.2：需求应聘与确认闭环

点击应聘时原子创建 PENDING Application、会话和首条消息。需求发布者可以接受、拒绝，申请人可以取消；接受后需求变为 MATCHED，其他申请进入 NEED_ENDED。发布者取消已选服务者后，未过期需求重新 OPEN。

若应聘者有服务档案，会话中提示需求方查看；没有则显示“暂无服务资料，请通过聊天了解经验”。

**完成标准**：应聘不等于成功；只有对方确认后状态变化；重复应聘、本人应聘、过期需求和并发接受测试通过。

### 任务 5.3：服务预约与确认闭环

预约请求必须选择明确时间段和宠物，原子创建 PENDING Booking、会话和消息。服务者可以确认、拒绝或取消确认，预约方可以取消；确认后才显示预约成功。服务暂停只阻止新预约，不取消已有预约。

**完成标准**：预约状态、参与者权限、时间合法性、服务状态和重复请求测试通过；服务详情能显示日期上的成功预约数量。

### 任务 5.4：寄养容量和并发控制

仅 BOARDING 服务应用容量限制，以重叠时间内 CONFIRMED 预约的宠物数量累计；其他模式不限制宠物容量。使用 PostgreSQL 事务/锁或等价并发安全方案，确认预约和容量扣减在同一事务中。

**完成标准**：边界容量、跨日重叠、取消释放、并发最后名额和不同服务隔离压测通过；不存在超卖。

### 阶段 5 验收

- “咨询 → 聊天”、“应聘 → 对方确认”、“预约 → 对方确认”三条闭环成立。
- 页面不再用本地布尔值表示业务成功。
- 状态变化、会话和通知事件在事务中保持一致。

## 10. 阶段 6：匹配、通知与邮件

### 任务 6.1：需求与服务双向匹配

发布需求后按模式、宠物、时间、距离、任务和预算匹配服务；无精确结果时推荐照顾相同宠物但类别可能不同的服务。发布服务后推荐匹配需求，无结果时推荐附近需求。匹配结果解释主要匹配原因，不隐藏筛选降级。

**完成标准**：精确匹配、降级匹配、附近结果和无结果四类测试通过；过期需求、暂停服务和本人内容不进入推荐。

### 任务 6.2：站内通知中心

建立通知事件、列表、未读数量和已读状态；覆盖消息、应聘、申请处理、预约请求、确认/取消和需求状态变化。替换导航和 Dashboard 中的 Mock 通知。

**完成标准**：事件去重、未读计数、参与者权限和链接目标测试通过；通知只能指向用户有权访问的资源。

### 任务 6.3：邮件偏好、Outbox 与可靠发送

在用户绑定并验证邮箱且开启偏好后，通过 Outbox 异步发送消息和业务状态提醒。发布成功后若尚未开启邮件通知，只提示一次是否开启。邮件不包含消息正文、地图坐标、精确位置或宠物健康信息。

**完成标准**：重试、去重、退订、失败恢复和模板三语言测试通过；停用 worker 不影响站内通知和核心事务。

### 阶段 6 验收

- 发布成功后的推荐分支符合确认后的规则。
- 消息和状态变化能形成真实站内通知。
- 邮件发送不阻塞主事务，隐私扫描通过。

## 11. 阶段 7：个人中心与完整使用体验

### 任务 7.1：需求、服务、应聘与预约管理中心

统一个人中心的信息架构，提供我的需求、我的服务、我的应聘、收到的应聘、我的预约、收到的预约和收藏。每个列表显示服务端真实状态和允许的下一步操作。

**完成标准**：不同身份和空状态正确；不存在指向 Mock 页或无操作死胡同的导航。

### 任务 7.2：服务批量管理和预约日历

在服务档案中支持暂停/开启全部服务、批量修改服务位置和货币，同时保留单项覆盖；提供服务预约日历，寄养日期显示已确认宠物数与剩余容量。

**完成标准**：批量操作只影响本人、事务部分失败可恢复、单项覆盖优先级清楚；已有预约不因暂停服务被取消。

### 任务 7.3：异常、冲突、草稿和可恢复体验

统一加载骨架、空状态、网络重试、并发冲突、草稿恢复、资源过期、无权限和业务取消说明。所有复杂表单提供错误摘要和步骤定位。

**完成标准**：断网/超时、重复提交、乐观锁冲突、草稿损坏和资源已变化 E2E 通过。

### 阶段 7 验收

- 用户不需要通过 URL 猜测管理入口。
- 所有状态操作都有可理解的影响说明和真实结果。
- 新旧 Dashboard 页面完成数据源统一。

## 12. 阶段 8：三语言、质量与迁移切流

### 任务 8.1：三语言内容和路由完整化

统一中文、英文、日文的导航、表单、错误、空状态、邮件、元数据、模式说明和知识分类。删除硬编码混合语言和测试文案，保持 key parity。

**完成标准**：三语言核心用户轨迹 E2E 通过；无缺失 key、页面混排或关键内容溢出。

### 任务 8.2：无障碍、响应式和性能收口

完成键盘、焦点、语义标签、错误播报、颜色对比、200% 缩放和常用移动宽度检查；拆分大型页面包，优化图片和字体加载，处理现有 lint 警告和不必要依赖。

**完成标准**：核心页面无阻塞级无障碍问题；性能预算、移动端视觉回归、lint/typecheck/build 通过；Google Fonts 不再成为不可控构建依赖。

### 任务 8.3：旧数据迁移、双读对账和灰度切流

在脱敏副本和 staging PostgreSQL 完成 migration、回填、双读对账和回滚演练。按 feature flag 依次切换档案、发布、公开市场、会话、容量和邮件；稳定一个发布周期后再制定旧字段/旧页面 contract migration。

**完成标准**：记录数、金额、宠物/附件关系、位置隐私和状态对账通过；关闭 flag 不丢失新数据；生产执行需要单独审批和备份确认。

### 任务 8.4：全流程验收与发布准入

执行游客浏览、新用户 onboarding、需求发布、服务发布、咨询、应聘、预约、取消、消息、通知、收藏、过期、档案管理和三语言完整回归。完成安全、隐私、性能和恢复性检查。

**完成标准**：P0 清零，P1 有明确处置；所有 CI 门禁和 staging E2E 通过；发布清单、回滚步骤和已知限制齐全。

### 阶段 8 验收

- 新数据模型和新页面成为正式事实来源。
- 旧路径只保留受控兼容或完成重定向。
- 未经批准不删除旧表和历史数据。
- 达到 MVP 公开发布条件。

## 14. 统一验收与提交规则

每个阶段内的任务完成后必须自行验收：

- 领域规则使用单元测试。
- 权限、事务、查询、迁移和容量使用集成测试。
- 核心用户轨迹使用桌面和移动 E2E。
- 页面任务检查键盘、焦点、错误恢复和三语言长度。
- 数据任务在临时数据库或脱敏副本完成，不直接操作生产数据。
- 新实现必须回归相关旧页面，防止融合过程中破坏已有能力。
- 成功提示必须以服务端成功为依据。
- 本地 QA 截图、渲染材料、字体缓存、测试数据库和浏览器 trace 不提交。
- 每个阶段输出验收报告、未完成项、P0/P1/P2 风险和下一阶段 Go/No-Go 结论。

## 15. 执行优先级

如果资源有限，必须遵循：

1. 安全与数据正确性高于新增页面。
2. 账号和档案高于发布功能接库。
3. 发布真实闭环高于推荐和邮件。
4. 应聘/预约服务端状态高于界面动画和视觉润色。
5. 数据迁移可回退高于提前删除旧实现。
6. 三语言核心路径和移动端可用属于 MVP，不作为上线后的可选优化。

建议下一步按阶段 1 开始执行；阶段 2 的详细任务文档已经准备好，但必须在阶段 1 权限和认证安全验收后进入其依赖部分。
