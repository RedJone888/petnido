# Petnido 第二批开发任务：安全、账号档案与后续开发基础

> 文档状态：待执行
> 编制日期：2026-08-04
> 适用分支：`codex/petnido-v2-development`
> 主要依据：`docs/reviews/next-iteration-board.md`、第一批审计与已确认的用户行为规则

## 1. 第二批定位

第二批不直接进入“完成新版需求发布和服务发布”。发布流程很重要，但当前项目还有更靠前的基础问题：写接口存在越权风险、认证缺少限流和统一错误、首次注册与普通登录没有正确分流、个人/宠物/位置档案不完整、服务档案开通流程缺失、登录前动作不能可靠恢复。

如果这些问题没有先解决，直接接通新版发布表单会把错误的权限、旧地址结构和不稳定的用户身份流程一起带入新功能，产生更多返工。

因此第二批按以下顺序推进：

1. 修复安全和服务端事实来源。
2. 建立账号、个人资料、宠物、位置和服务档案的数据基础。
3. 完成首次注册与非首次登录的真实用户流程。
4. 建立登录回跳、待执行动作和通知偏好基础。
5. 对新旧发布半成品做融合决策与技术准备，但不在本批切换正式发布入口。

第二批完成后，项目应达到“可以安全进入发布功能正式开发”的状态，而不是“发布功能已经完成”。

## 2. 本批目标结果

本批结束时应具备：

- 需求、服务和服务档案写操作不存在已知越权路径。
- 验证码具有基本限流、过期、尝试次数和日志脱敏保护。
- 新用户登录后依次完成头像昵称、意图选择；老用户直接进入个人中心。
- 用户可以维护个人资料、宠物档案和地图位置，不保存门牌、楼层、房号等精确地址文本。
- 用户选择提供服务时，必须确认开启接单模式，并能创建基础服务档案。
- 未登录用户触发收藏、咨询、应聘或预约时，登录后能安全恢复原页面和待执行动作。
- 未登录访问个人中心不再进入只有“请先登录”的死胡同。
- 邮件通知偏好已经具备数据和接口基础，但本批不实现完整邮件业务链路。
- 新旧发布需求/服务的可复用点、冲突字段和最终合同有逐项记录，为第三批实施提供输入。

## 3. 本批不包含

- 不接通新版步骤表单的正式数据库发布。
- 不切换 `/dashboard/needs/new` 到 `/needs/create`。
- 不完成寄养、自定义模式的发布事务。
- 不实现推荐算法、正式应聘/预约、聊天或邮件发送。
- 不实施寄养容量并发控制。
- 不删除旧发布页面、旧数据表或旧字段。
- 不执行生产数据库迁移或旧数据回填。
- 不包含支付、评价、运营和治理功能。

## 4. 第二批关键用户事例

### 事例 A：首次注册并选择发布需求

1. 用户完成注册或验证码登录。
2. 系统判断该账号尚未完成首次引导。
3. 用户填写头像和昵称；暂时跳过头像时使用安全默认头像。
4. 用户选择“我想发布需求”。
5. 系统进入需求发布入口，但在正式发布功能未完成前不得显示虚假的“发布成功”。
6. 已填写的个人资料保存在账号档案中。

### 事例 B：首次注册并选择提供服务

1. 用户完成头像和昵称。
2. 用户选择“我想提供服务”。
3. 页面询问“确认开启接单模式吗？”
4. 用户确认后创建服务档案，填写个人经验介绍、服务位置和常用货币。
5. 服务档案创建成功，但尚未创建具体服务时，应显示清楚的空状态和下一步入口。

### 事例 C：非首次用户登录

1. 已完成首次引导的用户登录。
2. 系统直接进入个人中心。
3. 不弹出“是否查看消息”的额外提示。
4. 用户自行从个人中心进入消息、需求、服务或资料页面。

### 事例 D：用户从公开页面触发登录动作

1. 游客在需求详情点击收藏、咨询或应聘，或在服务详情点击预约。
2. 系统保存签名且有过期时间的待执行动作，并进入登录。
3. 首次用户先完成首次引导；非首次用户完成登录后回到原详情。
4. 页面向用户确认一次，再执行动作；刷新或重复回跳不能重复创建业务记录。
5. 本批只完成通用恢复框架；业务 Router 尚未完成的动作返回明确的“功能准备中”，不能伪造成功状态。

### 事例 E：维护宠物和位置档案

1. 用户创建宠物档案，可以编辑并归档。
2. 用户在地图上选择位置并设置非精确区域标签。
3. 数据库存储经纬度和可选区域标签，不保存精确家庭地址文本。
4. 公开 DTO 不返回完整坐标、宠物健康信息或私有照护备注。

### 事例 F：越权访问

1. 用户甲尝试通过修改 URL 或请求参数编辑用户乙的需求、服务或档案。
2. 服务端数据库条件包含 owner ID，而不是只靠页面隐藏按钮。
3. 用户甲收到统一的 `NOT_FOUND`，用户乙的数据不发生变化。

## 7. 每项任务的自行验收规则

每完成一项任务，都必须：

1. 先执行该任务的单元测试和集成测试。
2. 执行受影响旧功能的回归测试，确认没有只顾新逻辑而破坏旧流程。
3. 页面任务至少检查桌面和 390px 移动端；关键表单增加键盘和 200% 缩放检查。
4. 数据任务检查 migration diff、空库迁移和脱敏数据 dry-run。
5. 权限任务至少使用 owner、非 owner 和游客三个身份测试。
6. 记录实际结果、证据路径、未解决项和后续归属。
7. 验收失败时不将任务标记完成，不继续执行依赖它的任务。

提交要求：

- 每项任务尽量形成独立提交，避免把多个领域混在一起。
- 不提交本地 QA 截图、渲染材料、字体缓存、测试数据库、Playwright trace 或真实用户数据。
- `git diff --check`、类型检查和该任务相关测试必须通过。
- 不在功能提交中顺手升级 Next、Prisma 或认证框架大版本。

### Go 条件

- B2-01 至 B2-13 全部完成独立验收。
- 已知写接口越权 P0 清零。
- 首次注册、非首次登录和登录回跳行为符合已确认轨迹。
- Profile、Pet、UserLocation、ServiceProfile 有稳定服务端事实来源。
- 没有新增精确地址落库和 Public DTO 泄露。
- 新旧发布流程融合矩阵完成，第三批可以按合同开发。

### No-Go 条件

以下任一情况存在，就不能进入发布流程正式接库：

- Need/Service/Profile 仍存在只按资源 ID 修改的接口。
- onboarding 只靠前端状态判断。
- 新位置数据仍写入 `addressRaw` / `baseAreaRaw`。
- 旧数据兼容读取没有 dry-run 和回退方案。
- 新版发布页面仍会在没有数据库写入时显示成功。
- PendingAction 可以被篡改、开放重定向或重复执行。
